Three concrete issues with this design:

1. **`begin()`/`cancel()` aren't actually wired up.** `Model.start()` sets `recordingDir`/`recording` directly but never calls `recordingNavigation.begin()`; `stop()` and the `launch(...)` completion handler (used for both the start-callback and `finalize`) never call `recordingNavigation.cancel()`. As written, `pending` is either never set (resolve always nil, selection never steals) or, once set by some other path, never cleared on stop/failure — so a stale `pending=true` from an aborted recording can fire on a later, unrelated recording.

2. **Stale `wanted` capture defeats the same-cycle refresh.** `refresh()` captures `let wanted = selected ?? ""` *before* the `await request(...)`. If `recordingNavigation.resolve()` then reassigns `selected = target` after the await, the later check `if wanted == selected` is now false, so `rows`/`refreshIntelligence` don't update for the newly-selected meeting in this cycle — the transcript pane will show the previous meeting's (or empty) rows until the next 2s tick, right at the moment the design intends selection to switch.

3. **No session token linking `resolve()`'s match to the `begin()` that set it.** The active-meeting match is done by comparing `capture_dir` to `recordingDir` read *after* the await, with no guard that this is still the same recording session that triggered `begin()`. If `stop()` is called and `start()` re-invoked (new UUID dir) while a snapshot request is in flight, the response is matched against the *new* `recordingDir`/`recording` state but reflects backend state from the old request — `pending` (if it were wired per issue 1) has no way to know it belongs to the prior session, so it can resolve/steal selection for the wrong recording, or fail to resolve for the one it was meant for.
