Two concrete issues with the proposed label mapping vs. actual `activity` strings:

1. **"Kayıt sürüyor" is shown before recording actually starts.** `start()` sets `recording=true` immediately, but the activity text at that point is `"Kayıt hazırlanıyor · macOS izinleri açık olmalı"`, and `refresh()` can then set it to `"macOS izinleri ve ses aygıtı bekleniyor…"` — both describe *waiting*, not recording. Since the sidebar card buckets purely on the `recording` flag, it will display the fixed label "Kayıt sürüyor" (recording in progress) right alongside text that says recording hasn't started yet. That's a direct contradiction the user will see every time they start a recording.

2. **Failures get folded into the neutral "Son durum" bucket with no visual distinction.** Error outcomes like `"Son işlem başarısız · Ses korunuyor"`, `"Dosya işlenemedi"`, and `"Kayıt kesildi · Arşivden sesi kurtarabilirsiniz"` all land in the idle state (`recording=false`, `busy=false`) once the job terminates. The spec only calls for a distinct treatment (red icon / progress) for recording and busy — idle failures render identically to the default "Hazır…" message and to export success text, just under the generic "Son durum" label. A real failure looks exactly like "nothing happened," which is worse than today where at least the text itself is the only signal (no misleading label reinforcing "everything's fine").

Recommend: gate the recording label on an actual capture-active signal (not just the `recording` bool) for issue 1, and add an error/warning treatment for idle-with-failure text for issue 2.
