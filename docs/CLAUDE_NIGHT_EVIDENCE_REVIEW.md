Three concrete issues with this design:

**1. "Missing segment" error fires too eagerly for meetings still loading.** Since pending is meant to be "consumed once after snapshot," a live/provisional meeting whose segments arrive incrementally (via the 2s poll) will trigger a false error the first time a snapshot lands without the target segment — even though it may show up on the very next poll. The plan doesn't gate the missing-segment check on `meeting.status` (processing/provisional vs. complete), so genuinely-not-yet-transcribed segments look identical to genuinely-deleted ones.

**2. Conflicts with the existing recording-navigation pinning.** While `recording == true`, `refresh()` unconditionally does `selected = recordingNavigation.resolve(active:)` on every poll. If evidence navigation sets `selected = e.meeting` to jump to a *different*, non-active meeting during a live recording, the next timer tick can immediately reassert `selected` back to the active recording, silently dropping the pending evidence jump. The design doesn't reconcile these two flows that both mutate `selected`.

**3. Nothing invalidates `pending` except a meeting change.** Resolution only happens on the ~2s polling cycle, and only `selected`'s didSet clears `pending`. If the user starts typing in search or switches tabs while a jump is queued, "typing clears focused segment" only touches `focusedSegment` — `pending` survives and will still hijack the tab/scroll position out from under the user once the snapshot arrives, since the plan gives no way for user-initiated navigation to cancel a queued resolution.
